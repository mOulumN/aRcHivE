# 도메인 브리프: 시각 레퍼런스 아카이빙·무드보드 앱

조사 날짜: 2026-11-04 (가벼운 웹 검색 기준. 아래 "확인 안 됨"은 직접 확인 못 한 것)

## 비슷한 제품
| 제품 | 성격 | 우리가 배울 점 | 우리와 다른 점 |
|---|---|---|---|
| Milanote | 무한 칠판에 사진·메모·링크를 끌어다 놓는 도구 ([출처](https://postmake.io/compare/milanote-vs-cosmos)) | 끌어다 놓기, 메모 카드 | 프로젝트 기획용. 사진 일부를 선으로 지목하는 기능은 확인 못 함 |
| Cosmos | 웹 콘텐츠를 모아 컬렉션으로 정리하는 시각 북마크 | 수집·큐레이션 격자 | 자유 기록이 아니라 모으기 중심 |
| Are.na | 차분하게 레퍼런스를 모으고 서로 연결 ([출처](https://www.inspoai.io/blogs/milanote-alternatives)) | 채널(계열) 개념, 느린 수집 | 글쓰기 기능은 약함 |
| tldraw / FigJam류 | 무한 캔버스 + 도형 | 선·도형 연결 | 범용 화이트보드. 아카이브 흐름 없음 |

결론: **"사진 일부를 지목해 선으로 빼낸 자유 메모 + 아카이브 보관함"** 조합은 조사에서 확인되지 않았다. 차별점이 될 수 있지만 "없다"고 단정은 못 한다.

## 구조 (보통 이렇게 만든다)
- 화면 2개가 기본: **모아보기(격자)** + **상세/편집(캔버스)**
- 분류는 폴더 또는 태그(Are.na의 채널처럼 한 사진이 여러 곳에 속할 수도)

## 데이터 구조 (Claude 판단)
- **기록(Entry)**: 사진 1장 + 메모들 + 계열 + 만든 날짜
- **메모(Note)**: 글, 위치, 배경색, 연결된 점(있으면)
- **점(Anchor)**: 사진 위 좌표(사진 크기 대비 비율로 저장 → 사진이 커지고 작아져도 같은 자리)
- **계열(Series)**: 이름 (예: UI, 자연). 기록은 계열 0~1개 (첫 버전). 
- 나중 확장: 프로젝트 = 기록들의 묶음 → 구조 바꿀 필요 없이 위에 한 층 추가

## 기능 구현 방식 (Claude 판단)
- **웹앱(PC 브라우저 우선)**: 드래그 앤 드롭이 핵심이라 PC에서 가장 자연스럽다.
- **캔버스**: 선택지 두 개.
  - tldraw: 완성도 높음, 하지만 운영 배포에는 라이선스 키가 필요([출처](https://github.com/tldraw/tldraw)). 상용 조건은 확인 못 함.
  - Konva(react-konva): 무료(MIT, 내 기억 기준, 이번 검색에선 확인 못 함). 이동·확대·되돌리기는 직접 만들어야 하지만 우리 화면은 단순해서 감당 가능.
  - → **Konva 쪽 추천**. 확정은 구현 단계에서.
- **문서로 뽑기(다음 버전)**: 기록 데이터를 "사진 + 문단 순서 목록"으로 바꿔 HTML/PDF 출력하는 구조. 메모에 순서가 있어야 하니 지금부터 메모에 "순서" 값을 가지게 설계해 둔다.

## 저장·배포
- **첫 버전은 로그인 없이 내 브라우저 안에만 저장(로컬 우선)**. 사진 파일은 OPFS(브라우저 안 파일 저장소), 글·점은 IndexedDB. 사진 저장소를 옮겨도 용량 한도는 같다([출처](https://web.dev/articles/storage-for-the-web)).
- 주의: 기본 상태에서는 저장 공간이 부족할 때 브라우저가 지울 수 있어, **"영구 저장 요청"** 을 켜야 한다. 그래도 브라우저 데이터를 지우면 사라지므로 **내보내기(백업) 기능**이 필요 (첫 버전에 간단히 포함 권장).
- 배포: 정적 웹사이트로 올리면 됨(Vercel/Netlify/GitHub Pages 등). 서버·DB 비용 없음.
- 나중에 폰·여러 기기 동기화가 필요해지면 클라우드 저장(로그인)을 추가 → ⏳

## 보안·개인정보
- 첫 버전은 서버가 없어서 사진이 내 컴퓨터 밖으로 안 나간다. 가장 큰 장점이자 안전한 설정.
- 클라우드·공유를 붙일 때 비로소 로그인, 사진 비공개 설정을 설계한다.
- 흔한 사고: 브라우저 데이터 삭제로 기록 전부 증발 → 백업 필수.

## 흔한 실패 패턴·사용자 기대
- 사진 넣고 쓰기까지 단계가 많으면 안 쓰게 된다 → 드롭하자마자 바로 칠판에서 쓰기
- 정리 체계가 무거우면 기록을 안 하게 된다 → 계열은 선택사항
- 큰 사진 여러 장이면 느려진다 → 저장 시 화면용 작은 사본도 같이 만들어 보관함에서는 작은 것 사용
- 점/선이 사진 크기를 바꿀 때 어긋나는 문제 → 비율 좌표로 저장

## 추가 조사: 폰(특히 아이폰)에서 기기 로컬 저장 (2026-11-04)
- 사파리는 사이트를 7일 이상 안 쓰면 그 사이트의 브라우저 저장 데이터(IndexedDB 등)를 지울 수 있다는 정책이 있다 ([출처](https://www.itnews.com.au/news/apple-cops-flak-for-deleting-local-browser-storage-after-7-days-539833)).
- **홈 화면에 추가한 웹앱은 사파리와 별도로 계산되고 이 제한에서 벗어난다**는 애플 엔지니어 설명이 있다 ([출처](https://mjtsai.com/blog/2020/03/26/safari-13-1-third-party-cookie-blocking-and-7-day-script-writeable-storage/)). 다만 자료가 2020~2022년 위주이고 보고가 엇갈려 **실제 아이폰 테스트로 확인 필요**.
- 대응: ① 아이폰은 홈 화면 추가 안내 ② 영구 저장 요청 ③ 백업(F-13)을 첫 버전에 포함 ④ 구현 단계에서 실기기 확인
- 안드로이드 크롬은 이 제한이 없는 것으로 알고 있으나 이번엔 확인 못 함.
