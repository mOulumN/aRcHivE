# 아이디어 보관함

확정된 결정이 아니라 **나중에 검토할 아이디어**를 모아 두는 곳. 확정되면 `결정.md`와 `구조.md`(기능 ID)로 옮긴다.

## 2026-11-05 — "쓸모 있게 쓰이려면" (사용자 제안, 지금 할 일 아님)

핵심 문제의식: 레퍼런스를 **모아 두는 것**은 만들었다. 이제 **실제로 꺼내 쓰는 흐름**이 있어야 진짜 쓸모가 생긴다. 예: Pinterest에서 보다가 좋은 사진을 바로 Claude 창으로 끌어다 쓰듯이, 이 앱에서 모은 사진을 다른 프로그램으로 바로 가져가 쓸 수 있어야 한다.

### 1. 다른 프로그램으로 끌어 놓기 (앱 밖으로 드래그 앤 드롭)
- 앱 창에서 다른 프로그램 창(Claude, 문서·디자인 도구 등)으로 사진을 끌어서 놓는다. 컴퓨터와 태블릿 모두 대상.
- **한 장씩도, 여러 장 묶음으로도** 가능해야 한다.
- 지금의 끌어놓기(프로젝트·카테고리로 옮기기)는 앱 **안**에서만 동작한다. 이건 앱 **밖**으로 나가는 별개 기능이다.
- 검토 메모(제안자 확인 필요):
  - 컴퓨터 프로그램(Electron)은 저장 폴더에 사진 원본이 실제 파일로 있어서 파일 끌기를 붙이기 쉬울 것으로 보인다. 여러 장 끌기가 되는지는 확인 필요.
  - 웹 미리보기는 브라우저 제한 때문에 방식이 달라질 수 있다.
  - 안드로이드·태블릿은 다른 앱으로 끌어 놓기를 시스템이 지원하는 범위가 앱마다 다를 수 있어 실기기 확인 필요.
  - 원본이 아니라 작은 사본(thumbs)이 나가지 않게 주의.

### 2. 미니 갤러리 (사진 보는 중에 옆에서 다른 사진 고르기)
- 지금은 사진 하나를 보다가 다른 사진을 보려면 목록으로 돌아가 다시 골라야 한다.
- 사진을 보고 있는 상태에서 **1열 미리보기 줄(미니 갤러리)**을 같이 보여 주고, 거기서 바로 다른 사진으로 넘어간다.
- 범위는 **카테고리 기준**이어도 되고, 그냥 **전체 나열**이어도 된다(둘 다 가능하게).
- 폰에서는 같은 아이디어를 화면 구성(F-42)에 맞게 다시 생각해야 한다.

### 3. 사진 원본 한 번에 빼기 (내보내기)
- 사용자가 원본을 **따로 파일로 보관**하고 싶을 때, 사진을 여러 장 선택해서 **원본 파일만** 한 번에 뽑아낸다.
- 지금의 백업(내보내기 ZIP)은 앱 전체 데이터용이다. 이건 **선택한 사진의 원본만** 꺼내는 별개 기능이다.
- 이 기능은 1번(앱 밖으로 끌어 놓기)과 짝으로 쓰일 수 있다: 끌기 = 바로 쓰기, 뽑기 = 파일로 보관.

### 4. "보관"에서 "쓰기"로 가는 흐름 (열린 질문)
- 모으는 것은 만들었고, **실제로 사용하는 흐름을 어떻게 만들지**는 아직 모른다. 고민이 필요하다.
- 던져 볼 질문:
  - 모은 사진을 가장 자주 어디로 가져가는가? (AI 채팅, 디자인 도구, 문서, 메신저 등)
  - 사진에 붙인 **지목 영역과 메모**도 함께 가져가야 하는가, 사진만 필요한가?
  - 사진 + 메모를 한 덩어리 글(예: 설명 문서)로 뽑는 기능(F-09 문서로 뽑기)과 어떻게 이어지는가?
  - 프로젝트 단위로 "이번 작업에 쓸 것"을 모아 한 번에 내보내는 흐름이 필요한가?
- 이 질문에 답이 정해지면 1~3번의 우선순위가 정해진다.

### 관련 기존 항목
- F-09 문서로 뽑기, F-39~F-43(통합·메모·홈·폰·검색)과 겹치는 부분을 정리할 것.
- 방향성(`방향성.md`)의 "하지 않을 것"과 충돌하지 않는지 확인 후 확정.

## 2026-11-05 — 폰 맵 화면 추가 수정 사항 (사용자 요청, 지금 할 일 아님)

사용자는 현재 디자인이 마음에 든다고 했다. **디자인은 바꾸지 말고** 아래 사용성만 고친다(`규칙.md`의 `--btn-py`, `--select-w` 규칙 유지). 대상은 폰(767px 이하) 맵 화면.

1. **맵 진입 시 중심으로 안내**: 맵을 누르면 폰 화면이 사진이 모여 있는 곳의 중심점으로 가도록 한다. (지금은 처음 위치가 사진 무리와 어긋나 찾아야 하는 상황으로 보임. 중심 = 맵에 놓인 사진들의 가운데, 확대 배율도 함께 정할지는 확인 필요)
2. **"기준" 블록을 점 세 개 왼쪽으로 꺼내기**: 점 세 개(···)를 눌러 들어가서 기준을 고르는 것이 불편하다. 점 세 개는 앞으로 다른 용도(더보기)로 쓸 수 있으니 남겨 두고, 기준 블록 자체를 그 **왼쪽에 바로 보이게** 옮긴다.
3. **하단 창이 가장 아래 사진을 가리는 문제**: 맵 아래 길이가 고정돼 있어서 "선택"·"기준" 하단 창을 열면 그림이 가려진다. **가장 아래에 있는 사진을 기준으로, 하단 창 높이만큼 맵 아래 여백을 더 늘려서** 창이 열려 있어도 맨 아래 사진까지 스크롤해서 볼 수 있게 한다. (창이 닫히면 여백도 원래대로인지는 정해야 함)
4. **선택 취소 방법**: 선택 창에 취소가 없다. 선택 중에 **"선택"을 한 번 더 누르면 취소**되게 하거나 취소 버튼을 둔다. (사용자는 둘 중 아무거나 좋다고 함. 하나로 통일 필요)
5. **하단 창 버튼을 터치하기 쉽게**: 선택·기준 하단 창의 "선택 / 접기 / 완료" 버튼이 작다. 글자를 **아주 조금만** 키우고, **버튼 사이 간격을 더 띄운다**. `규칙.md`에 "폰에서 터치 높이를 키울 땐 줄 전체를 같이 키운다"가 있으니 같은 줄 요소를 함께 키운다.

해당 코드 후보: 맵 화면(`src/components/MapView.tsx`, `mapLayout.ts`), 하단 선택·기준 창(`SelectPanel.tsx`, `BaseTagPicker.tsx`, `FloatingPanel.tsx`), 폰 CSS(`app.css`의 767px 이하 구간).

## 2026-11-05 — 사진 확대·축소 시 메모 크기 문제 (사용자 고민, 수정 사항으로 올려만 둠)

**지금 문제:** 사진을 확대·축소해서 볼 때 메모의 **글자 크기는 그대로인데 메모 칸의 가로·세로 크기는 계속 바뀐다.** 이 조합이 애매하다(글자는 고정, 칸은 변하니 글이 넘치거나 남는다).

사용자가 원하는 것:
1. 사진을 확대·축소해서 볼 수 있어야 한다.
2. 메모 칸은 **내가 정한 크기 그대로** 유지되면 좋겠다.
3. 다만 기본으로 주어진 사진 크기가 마음에 안 들 수도 있다. 어떤 사용자는 글자 크기와 메모 칸 크기는 그대로 두고 **사진 기본 크기만 더 크게(또는 더 작게)** 하고 싶을 수 있다.
4. 그래서 **개별 설정(글자 크기, 메모 칸 크기, 사진 기본 크기)이 따로 가능**하되, 확대·축소할 때는 **전체가 한꺼번에 같은 비율로** 커지고 작아지는 쪽이 낫겠다는 생각.

정리해 둔 방향(확정 아님):
- 확대·축소는 사진, 지목, 메모(글자·칸)를 **하나의 판처럼 같은 비율로** 움직인다. 그러면 칸 크기와 글자 크기의 비율이 깨지지 않는다.
- 사진 기본 크기·글자 크기·메모 칸 기본 크기는 **설정에서 각각 바꿀 수 있게** 한다. 사진 기본 크기만 바꿔도 메모 칸은 그대로 남는다.
- 지금 코드는 지목 위치를 "사진 가로 길이 = 1" 비율로 저장하므로(`규칙.md`), 메모 위치·칸 크기를 사진 기준 비율로 둘지 화면 기준으로 둘지가 설계의 핵심이다.

**확인이 필요한 질문(만들기 전에 사용자에게):**
- 4번의 "그대로 두고 전체 다 확대 축소"는 "글자도 칸도 사진과 같이 커지고 작아진다"는 뜻인가, 아니면 "설정한 크기는 기본값으로 두고 확대·축소는 화면 배율일 뿐"이라는 뜻인가? (아마 같은 말이지만 확인)
- 확대하면 글자도 같이 커지는 것이 맞는가? (지금은 글자가 고정이라 큰 사진에서 글이 작아 보일 수 있다)
- 사진 기본 크기 설정은 전체 공통인가, 카테고리·프로젝트별인가?
- 폰에서의 핀치 확대와 컴퓨터의 휠 확대가 같은 규칙을 따라야 하는가?

관련: 맵·프로젝트 보드의 메모 글자 크기 설정(기본 고정 메모 14px), `useZoom.tsx`, 메모 칸 크기 조절(F-24 `Note.w/h`).

### 추가 (같은 날): "원래 크기로 되돌렸을 때 처음 설정한 메모 크기가 아니다"

사용자가 짚은 핵심: 확대·축소가 애매한 진짜 이유는, **메모 크기를 정해 두고 확대·축소를 마구 한 뒤 원래 배율로 되돌렸을 때 처음 정한 메모 칸 크기로 돌아오지 않는다**는 점이다. 그래서 규칙 이전에 **"되돌리면 원래대로 돌아온다(왕복해도 값이 변하지 않는다)"** 가 지켜져야 한다.

- 설계 기준으로 삼을 것: **저장된 메모 크기는 확대·축소로 절대 바뀌지 않는다.** 배율은 화면에 보이는 모양만 바꾸고, 저장 값(`Note.w`, `Note.h`)은 사용자가 직접 칸을 늘이거나 줄였을 때만 바뀐다. 이 기준이면 아무리 확대·축소해도 100%로 돌아오면 처음 크기다.
- 검토 메모(코드를 읽고 한 **추정**, 확인 필요): 사진 보기 화면(`screens/Board.tsx`)의 메모는 글 길이에 맞춰 높이가 자동으로 늘고, 그 높이를 `ResizeObserver`가 읽어 저장 쪽(`onHeight`)으로 되돌려 주는 구조다. 배율이 바뀌어 글이 다시 줄바꿈되면 그 "읽은 높이"가 저장 값을 덮어써서 왕복 때 값이 어긋날 가능성이 있다. 맵 메모(`components/MapNotes.tsx`)도 `offsetHeight`를 읽는 곳이 있다. 실제로 값이 바뀌는지 먼저 재현해서 확인한 뒤 고친다.
- 정해야 할 것: 칸 높이를 **사용자가 늘린 값(`h`)만 저장하고 글에 따른 자동 높이는 저장하지 않는지**, 확대·축소 중에 글자도 같이 비율로 커지게 할지(그러면 줄바꿈이 배율과 무관하게 같아져서 어긋남이 사라진다).
- 이 항목이 위 "사진 확대·축소 시 메모 크기" 설계의 **첫 번째 조건**이다. 다른 설정(사진 기본 크기 등)을 넣기 전에 왕복 시험(확대·축소를 여러 번 한 뒤 100%로 돌아와 저장 값 비교)부터 통과하게 한다.
